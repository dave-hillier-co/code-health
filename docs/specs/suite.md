# Code Health Suite — Spec

This spec covers the conventions shared by every plugin in this marketplace. Each plugin spec ([locality](locality.md), [cochange](cochange.md) with its [abandonment](abandonment.md), [identities](identities.md) and [change-risk](change-risk.md) skills, [complexity](complexity.md), [structure](structure.md) with its [packaging](packaging.md) skill) assumes this one, and [red-flags.md](../../shared/red-flags.md) is the shared design vocabulary.

## Purpose

The suite is a set of Claude Code plugins that find where code is expensive to change, guide agents in fixing it, and measure whether changes really got cheaper. Each plugin pairs a deterministic CLI that computes facts with a skill that holds policy and judgement.

## Applicability

The suite is built for **medium to large monolithic codebases**: single applications, modular monoliths and monorepos where the code that changes together lives in one repository and depends through imports, includes or references. That is where distance, cohesion and co-change carry signal, and where an agent's navigation cost grows with size.

It is a poor fit for **microservice estates**. In a repository per service, each repository is small, so locality is trivially satisfied, and the coupling that matters crosses services through APIs, messages and shared schemas. No import graph or single history shows it. That needs different tools (contract and schema analysis, cross-repository co-change, tracing), outside this suite.

**Maturity strengthens the evidence.** History-based signals (co-change, hotspots, abandonment, change stability, grace periods) need history. A mature codebase, with years of commits, many contributors and many logical changes per file, gives strong co-change evidence. A young one gives weak evidence: a few shared commits are indistinguishable from chance, and much of the code has not yet had time to be reused. Plugins therefore measure evidence strength and report it (see [Evidence strength](#evidence-strength)). On young codebases, static signals carry the recommendations and history-based ones are labelled tentative.

Monorepos that hold several services sit in between. Each service's package boundary is a fixed point that no move crosses. The plugins work within each service. Cochange still sees across them, and frequent co-change between services is reported as evidence of a distributed monolith. Fixing that is outside the suite.

## Principles

These apply to every plugin, and a plugin spec that departs from one must say why.

1. **Outcomes over scores.** Every plugin names an outcome measure (change spread, change cost, agent effort) and treats its own static score as a leading indicator only. Any score that is optimised alone gets gamed, so each plugin also names its gaming check.
2. **Determinism where mechanical, judgement where semantic.** The CLI computes facts and deterministic recommendations, so the same inputs (repo, config and history, plus any extras the output declares, see [CLI contract](#cli-contract)) produce byte-identical JSON. The agent supplies judgement and records every override with a reason.
3. **CLIs report, they do not edit.** Analysis commands never modify code. Mechanical edit commands (such as the locality mover) are separate, default to a dry run, and need `--apply`.
4. **One refactoring per commit.** Every applied change is a single, revertible step with tests green before and after. A reviewer never evaluates a move and a behaviour change together.
5. **Evidence beats convention.** Folder conventions, anticipated reuse and metric guidelines are hypotheses. History and consumer evidence decide. The rule of three marks when to *consider* removing duplication or keeping an abstraction. It is never a mechanical rule in either direction.
6. **Deep over shallow, and inline by default.** Remedies hide decisions behind simple interfaces. Inlining single-use indirection is a first-class remedy (Carmack, Blow). No plugin creates new shared helpers or abstractions, and any extraction stays local (see [red-flags.md](../../shared/red-flags.md)). The one stated exception is dependency breaking in [structure](structure.md#decisions).
7. **Scrutinise what is widely used.** High fan-in multiplies the cost of every flaw. Utilities with many consumers have earned their location, and they are the first place to check for red flags.
8. **Built for agents, usable by people.** Output is compact, ranked and limited by default. JSON is the contract, and a human-readable table is the default view in a terminal.
9. **Local and private.** No network access, no telemetry. Data about people is off by default. The exceptions (identity resolution, successor names, an author's placement to their own change) are stated and bounded in their own specs.
10. **Self-contained plugins, composed by data.** No plugin requires another at runtime. They share code at build time and exchange results through files.
11. **Patterns emerge from the codebase.** Where a remedy involves a design mechanism (an interface, events, a mediator), skills prefer what the codebase already uses nearby and ask before introducing anything new. No skill defaults to a named pattern. CLIs provide the census of what exists; the agent chooses.
12. **Guidelines, not hard limits.** A numeric value from CodeScene, a book or a judgement call orders and annotates results. It never hides, drops or fails them (see [Guidelines](#guidelines)).
13. **Language-agnostic first.** As much as possible works from history, indentation and lexical structure, which apply to every language and every historical revision. Language adapters add precision where the agnostic layer cannot answer: import resolution, exact metric definitions, deterministic moves. The lexical layer is the lowest common denominator, and language support beyond it is best effort: a repository in a language with no adapter still gets the history layer and whatever the lexical layer can measure.

## Repository layout

The repository is both the marketplace and the source monorepo.

```
.claude-plugin/marketplace.json     marketplace manifest
plugins/                            what users install; one self-contained folder each
  <plugin>/
    .claude-plugin/plugin.json
    skills/<skill>/SKILL.md
    skills/<skill>/references/*.md  loaded on demand (incl. generated red-flags.md and reports.md)
    dist/<plugin>.mjs               bundled CLI (built, committed)
    dist/chunk-<hash>.mjs           modules a command imports on demand, only if the plugin has any
    dist/grammars/*.wasm            tree-sitter grammars, only if the plugin parses
    schemas/*.schema.json           JSON Schemas for every --json output
    evals/<case>/                   claude plugin eval cases
packages/                           source; never installed directly
  cli-kit/                          argument parsing, output, exit codes, config loading
  history/                          git ingestion and the shared cache
  report/                           the report slot protocol, page shell and components
  lexical/                          lexer profiles, indentation, function blocks, hunk shapes
  parse/                            web-tree-sitter loading and language adapters
  graph/                            import graphs, dominators, tree distance
  <plugin>/                         each plugin's CLI source and tests
shared/red-flags.md                 single source, copied into each skill's references
shared/reports.md                   how an agent writes a report's judgement, copied likewise
docs/specs/                         these specs
fixtures/                           scripts that build deterministic fixture repos, and languages/<id>/ conformance fixtures
```

Rules:

- **Installed plugins are copied** to `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`. Nothing outside the plugin folder is copied, and paths that escape it are rejected. Shared code therefore reaches a plugin only by bundling: esbuild bundles each CLI with its `packages/*` dependencies into one ESM file in `dist/`. A module a command loads with `import()` goes in a content-named `chunk-<hash>.mjs` beside it, read only when that command runs, so a large dependency (locality's ts-morph) does not slow every start. Chunks are plain ESM files in the same folder, so there is still no runtime install.
- **`dist/` is committed**, because installation is a git copy with no build step. CI rebuilds every plugin and fails if `dist/` differs from the committed build, so the shipped bundle always matches its source.
- **No runtime npm install.** Bundles have no external dependencies. WASM assets sit next to the bundle and are resolved relative to `import.meta.url`.
- **No `index.ts` barrel files.** Modules are imported by their real path, which keeps the suite's own import graph honest for the locality analyser.
- **No top-level `bin/`.** It would put the CLI on the Bash PATH, but claude.ai and Cowork do not install plugins that contain one. Skills call `node ${CLAUDE_PLUGIN_ROOT}/dist/<plugin>.mjs` instead.
- **Plugin names** are kebab-case and avoid the reserved prefixes (`claude-`, `anthropic-`, `cc-plugin-`).

## Plugin anatomy

### plugin.json

Each plugin's manifest is `name`, `displayName`, `version`, `description`, `author`, `license`, `repository`, `keywords` and `engines.claude-code`. The version is set **in plugin.json only**, never also in the marketplace entry: plugin.json would win there, with only a `claude plugin validate` warning to show for it. Users of a third-party marketplace get updates only when the version string changes, so once the marketplace is published CI fails a change under `plugins/<plugin>/` that does not bump that plugin's version. Until then every plugin stays at `0.1.0` and no bump is required.

### Skills

- One skill per user question, not per CLI command. Most plugins need one skill. A second is justified when it is triggered by a different situation, such as a pre-change briefing versus a periodic review.
- `SKILL.md` stays under 500 lines and holds the workflow, decision policy and commit discipline. Guideline tables and long explanations go in `references/`, loaded on demand. Every line of SKILL.md is a recurring token cost.
- The `description` says when to use the skill in the user's terms ("before refactoring", "code that is hard to change", "what usually changes with this file") and is covered by trigger evals.
- `allowed-tools` pre-approves the plugin's own CLI so runs do not prompt each time: `Bash(node ${CLAUDE_PLUGIN_ROOT}/dist/<plugin>.mjs *)`. It never approves anything broader.
- `${CLAUDE_PLUGIN_ROOT}` is substituted in skill content but is **not** in the environment of Bash commands, so skill text writes the CLI path out in full through substitution and never relies on the variable at runtime.
- **No hooks.** Plugins register no hooks, so nothing is injected into a session that the user did not ask for. Claude runs the CLI on request, as its skills direct, for example `cochange brief` before it changes a file.

### Configuration

All plugins read one committed file at the repo root, `code-health.json`, with a `$schema` reference. It has a top-level `exclude`, `testPatterns`, `languages`, `entryPoints`, `includeRoots`, `components`, `vagueNames` and `history` shared by every plugin, and one section per plugin. `testPatterns` is a list of globs that decide which files are tests, laid over each language adapter's naming conventions (`isTestPath`): a match makes a file a test, an entry that starts with `!` makes it production, and the last matching entry wins. `languages` is an object from a lower-case file extension without its dot to a lexer profile name. The JSON Schema it points to is generated from every plugin's config section and checked in CI. Each plugin validates its own section and ignores the values of the others. Missing config means defaults.

**An unknown key is an error.** A top-level key that is not `$schema`, a shared key or the name of a plugin section, and a key inside a plugin's section that the section does not define, make the command exit with 2 and name the key and the known ones. This is the same rule the generated schema states, so a misspelt key fails the same way whether or not the editor validates.

**Shared history settings.** The top-level `history` section holds how history is read, once for the whole repository, so that every plugin analyses the same window of the same commits (CodeScene likewise has one analysis period per project). Its keys, with their defaults, are `branch` (null, which analyses HEAD), `firstParent` (false), `renameSimilarity` (50, percent), `renameLimit` (1000), `windowMonths` (12), `maxChangesetSize` (30), `botPatterns` (an empty list), `fixPatterns`, `revertPatterns`, `fixMatchBody` (the definition of a fix commit, below) and `evidence` (the guidelines that grade the evidence of a history: `strong` and `moderate`, each with `months`, `logicalChanges` and `contributors`). A plugin section may override any of these keys that the plugin reads, under the same name, for example `cochange.windowMonths`. Each plugin spec lists the keys it reads, and a section that sets a history key its plugin does not read is an unknown setting. The effective value of a key is the plugin's own value when its section sets one, otherwise the `history` value, otherwise the default. Objects merge key by key (setting `cochange.evidence.strong.months` leaves the rest of `history.evidence` in place), and lists and scalars replace. A `null` override replaces a shared value. The effective config that the config hash covers holds the resolved plugin values and the `history` section, so changing either changes the hash. `config explain` prints a plugin's history value with the source of whichever level supplied it. A value that is out of range names the path it was written at, `history.windowMonths` or `cochange.windowMonths`.

**Guidelines in config** are named as guidelines, with the source of the default recorded beside it (see [Guidelines](#guidelines)).

**Fix commits.** One definition of a fix serves every plugin that counts fixes (change-risk's `defect-history` factor and backtest, the complexity outcome comparison, `cochange fixes` and the fix columns of hotspots, and any later statistic), implemented once in `packages/history` (`fix-commits` for the patterns, `landings` for what is classified). **Fixes are counted per change that landed on the main line**, because a fix made on a branch before it merged was caught in review and is not a regression. A *landed change* is a commit on the first-parent line of the analysed ref together with, for a merge commit, the commits that only its later parents reach. It is classified by its own text and by nothing else: for a squash, rebase or direct commit that is the commit message, and for a merge commit it is the pull request title. GitHub writes the title in the body of "Merge pull request #N from owner/branch" (the first line after the blank one), some repositories put it in the subject ("Merge pull request #681: title"), and GitLab writes it after "Merge branch 'x' into 'main'" with a trailing "See merge request" line that is not the title. A merge that names no title is classified by its own subject. The commits reachable only through a merge's later parents belong to the landed change and are never classified as changes: their fix-like subjects are listed apart as **fixes during review**, with a count and the commits as evidence, on the file and function rows of `cochange fixes`, `complexity fixes` and the fix columns of `cochange hotspots`, and are never counted in a fix count. A repository that merges by fast-forward or rebase has no merge commits, so each of its commits is a landed change and a fix made before the merge cannot be told from one made after. Revisions in a fix share are counted over the same landed changes: `cochange hotspots` reports `frequency` as every commit that touched a file, as it always has, and its `fixShare` and that of `cochange fixes` are fixes over `landedChanges`, the landed changes that touched the file, so a share compares like with like; `complexity fixes` counts a function's `unitRevisions` over landed changes. `history.fixPatterns` is a list of case-insensitive regular expressions matched against the landed change's text, the subject of a commit or the pull request title of a merge. The defaults are a Conventional Commits `fix:` or `fix(scope):` prefix, a merge of a fix/, hotfix/ or bugfix/ branch (a merge whose message names no title), fix, fixes, fixed or fixing at the start of the subject (after an optional Conventional Commits type or scope, or a ticket prefix such as "ABC-123:") or after "to" ("... to fix the crash"), "Fix #123" and "Fixes #123" anywhere in the subject, a subject starting "Review fixes", and the whole words bug, bugs, bugfix, hotfix and defect anywhere. The word "issue" is not a default, and fix words in the middle of a subject do not match, so "Add fixed clock" and "Describe fix commits" are not fixes. `history.fixExcludePatterns` is a guideline list, a judgement call not calibrated on a corpus, of expressions matched against the subject of a landed change that a fix pattern matched: a match means the change is not a defect fix, and it is counted as excluded, with the pattern that excluded it, and not as a fix. The defaults are two rules. (1) When a subject has a Conventional Commits type prefix, the type decides: fix and fix(scope) are fixes, chore, ci, test, docs, style, build, refactor and perf are not fixes even when "fix" appears later in the subject ("chore: fix docker-composes", "test: fix flaky TestExecuteRepair"), and revert is a revert. A type the list does not name, such as feat, leaves the subject to the rules for a subject without a type. (2) A fix whose target is typos, spelling, lint or formatting, within three words after the fix word ("Fix typo", "fix: lints"). A follow-up to review comments is not excluded: made on a branch it is a fix during review, and made on the main line it is a change like any other. A repair of tests or CI is a fix, because it repairs a defect in the test or CI code ("Fix three GPU test failures that turn CI red", "fix: flaky TestExecuteRepair"). Every count of fixes reports the number it excluded, by excluding pattern. Commit bodies are not matched by default, because "Fixes #123" trailers close any kind of issue, and `history.fixMatchBody` (default false) turns body matching on. The patterns are a judgement call and produce false positives and misses, so every count of fixes keeps the matching changes, each with the pattern that matched it, and prints how many it omits beyond its limit. `history.revertPatterns` (default a subject starting with Revert) and the "This reverts commit" body line that git writes classify reverts separately, and a revert is never counted as a fix. A plugin section that lists these keys (`fixPatterns`, `fixExcludePatterns`, `revertPatterns`, `fixMatchBody`) may override them, for example `cochange.fixPatterns`. `cochange.risk.fixPatterns` and `cochange.risk.revertPatterns` no longer exist, and a config file that sets them exits with 2 and names `history.fixPatterns`.

**Fix convention check.** Before a command reports a fix count, it runs the repository-level check, which decides whether the titles of the landed changes in its window use a recognisable fix form: Conventional Commits types (`feat:`, `fix(scope):`), a leading Fix, Fixes, Fixed or Fixing (after an optional ticket prefix), or a closing keyword with an issue reference ("Fixes #12", "Closes ABC-12"). A pull request number alone, as in "Add retries (#12)", is not an issue reference. The verdict `followsConvention` is true when any form is seen, and it is not decided by the share of fixes: a repository with few fixes and a clear form is not flagged. The result reports `forms` (how many titles used each form), the landed changes and fixes counted, and the `share` of fixes over landed changes as information beside the form evidence. When no form is seen the result carries a note saying the commit messages probably do not follow a convention this can use, the counts are still reported and nothing is removed.

**Built-in excludes.** Every plugin always leaves out, in its source trees and in its history filters, the files that match any of these entries, whatever the config says:

- `.claude/**`, `.cache/**` and `.code-health/**`, each anchored at the repo root;
- every file below a directory under the repo root that is its own git checkout, that is, a directory that contains a `.git` file or directory (a linked worktree, a nested clone) or a submodule recorded in the tree as a commit.

The config `exclude` adds to this list and does not replace it, and nothing unsets an entry. `config explain` prints each built-in entry with the source `built-in`, in rows `exclude.built-in[0]` to `exclude.built-in[3]`. The analysed root is `git rev-parse --show-toplevel` of the working directory. A command run inside a linked worktree therefore analyses that worktree, with its own files, and a command run in the main folder analyses only the main checkout: a worktree below it (Claude Code keeps them in `.claude/worktrees/`) is a nested checkout and is left out. The entries apply to every enumeration of files: trees read from a revision or from the working tree, untracked files, the files that manifests, package, tsconfig, Go module and C# project discovery read, and the paths of commits in the history filters, the blame listing and the files of a branch change.

Each command that left files out because of a built-in entry says how many. The JSON document has `omittedByBuiltinExcludes`, an object from entry (`.claude/**`, `.cache/**`, `.code-health/**`, or `<directory below the repo root that contains .git>`) to the number of distinct files it omitted, with entries that omitted nothing left out, and the key is absent when none did. A table run prints a `Notice: built-in excludes omitted` line with the same counts. A file is counted once per entry however many times it was met, whether in a tree or in history, and when a path matches more than one entry the first in the order above takes it. A checkout directory that git lists as a single untracked entry is counted by the files it holds (its tracked files and its untracked files that are not ignored). A command that reads only committed files (history, or a revision) does not look at untracked directories, so its counts are of the committed files it met.

**Generated and vendored files.** One filter, `classifyFiles` in `packages/history` (`file-class`), decides which files are generated or vendored, and every plugin uses it for its source trees (a revision, the working tree) and for the paths of history commands (hotspots, coupling, clusters, fixes, age, risk, blame and abandonment, and the other plugins' history evidence). A file is left out when any of these holds:

- it is generated: `.gitattributes` marks it `linguist-generated` (as git evaluates it: nested files, patterns and negation), or one of the first 20 lines of the file is a comment line (starting with `//`, `/*`, `*`, `#`, `--`, `;`, `%`, `<!--` or `'`) that carries a marker: `<auto-generated` (C#), `Code generated ... DO NOT EDIT` (Go), `@generated` (many generators), `Generated by`, or `DO NOT EDIT`;
- it is vendored: `.gitattributes` marks it `linguist-vendored`, or it lies below a directory named `vendor` or `third_party` at any depth (`node_modules` is a built-in exclude);
- a glob of the config `exclude` matches it (a repository's build output belongs there).

A header is read from the blob at the analysed revision, once, and the verdict is kept by blob SHA, so a blob met again is not read again. A history path that no longer exists at the analysed revision has no blob there, so it is decided by attributes and directory alone. A file named like a binary (an image, an archive, model weights) is not read for a header. A Go file that carries the generated header is also left out by the Go adapter, which lists it under `generatedFiles` in the analysis of a tree that was not filtered.

Each command says how many files the filter left out. The JSON document has `dropped`, an object with `generated`, `vendored`, `nonCode` and `tests` (below), each the number of distinct files left out in that run, and the key is absent when nothing was left out. A table run prints a `Notice: omitted` line with the same counts. A file that is generated is counted as generated and not also as vendored. History commands also print `filtersApplied.dropped`, which counts by change entry (the same file in two commits counts twice), where `dropped` counts distinct files.

A false positive is opted back in by unsetting the attribute for the path (`-linguist-generated`, `linguist-generated=false`, `-linguist-vendored`, or `linguist-vendored=false`, which also overrides the header and the vendor directory), or by removing the `exclude` glob. A file that carries a marker on purpose is generated by this definition, and one that does not want that removes the line. Hand-written schemas and contracts under `plugins/*/schemas` carry no marker, so they stay in the results.

**Code and non-code files.** A file is code when a language adapter or a lexical profile claims it: the extensions of a supported adapter, of a built-in lexer profile, or of the config `languages`. Every other file is non-code: lockfiles (`package-lock.json`, `yarn.lock`, `pnpm-lock.yaml`, `go.sum`, `Cargo.lock`, `packages.lock.json`), changelogs and other documents, JSON and YAML data, images, glTF and model weights, binaries, goldens, and a file without a claimed extension. The class is `isCodePath` in `packages/parse` (`code-files`). It applies this way:

- `complexity files` ranks code only.
- `cochange hotspots`, `fixes` and `age`, and the rankings built on them (`brief`, the abandonment ranking), rank code only, and `--all-files` ranks the non-code files as well. With `--all-files` a non-code file has a complexity only when the complexity report lists it, and is otherwise unscored. A run with `--all-files` is not stored as a report.
- `cochange coupling` includes non-code files, because a lockfile that changes with its manifest is real coupling, and labels each side of a pair as `pathKind` and `withKind`, `code` or `non-code`.
- The non-code files that a ranking left out are counted in `dropped.nonCode`, and a run that includes them has `inputs.allFiles` true.
- **Test files.** A ranking that lists production code first (`complexity files`, `cochange hotspots` and the rankings built on it) leaves out the test files, as decided by the language conventions and `testPatterns`, counts them in `dropped.tests`, and lists them with their `role` when `--include-tests` is given, in which case `inputs.includeTests` is true.

CodeScene has no automatic detection and excludes by configured patterns. The suite adds `.gitattributes` because it is the repository's own statement and other tools read it, and the header markers because generators write them. Every CLI has `config explain` to print the effective config and where each value came from, so the skill can explain it. Plugin `userConfig` is not used, because these settings belong to the repository, not the user.

## CLI contract

Every plugin's CLI follows the same conventions, implemented once in `packages/cli-kit`.

- **Invocation.** `node <dist>/<plugin>.mjs <command> [options]`. It needs Node ≥ 22.13 for unflagged `node:sqlite`, and the CLI suppresses its experimental warning.
- **Output.** A table on a TTY. JSON with `--json`, or whenever stdout is not a TTY. Every JSON document has `schemaVersion`, `tool`, `command`, `repo` (HEAD SHA and dirty flag), `config` (hash of effective config), `inputs`, `results`, `truncated` and `meta`. Wall-clock timestamps, timings and the git version appear only in `meta`, which golden comparisons ignore, so outputs stay diffable. A command that may store a report also puts `report` in `meta`: `{ "stored": true }`, or `{ "stored": false, "reason": "..." }`, and its table view prints a line when nothing was stored (see [Shared caches](#shared-caches)).
- **Determinism.** Results are sorted by `ranking.ratio` (how far past its guideline a row is) when the rows have one, then by score, then by path. Paths are repo-relative POSIX. Floats are rounded to a fixed precision. Golden tests enforce byte-identical output. Time is anchored to HEAD's committer date, never the wall clock: analysis windows, code age, grace periods and activity windows are all measured back from it. Anything a result depends on beyond the repo, config and history (a sibling plugin's report, local overrides, session transcripts) is named in `inputs` with its stamp or hash, and byte-identical output is promised for identical inputs.
- **Size discipline.** List commands default to `--limit 20`, take `--fields` to project columns, and report how many results were cut. `--limit all` removes the cap. An agent should never receive a 5,000-row dump by accident. The cap is the only thing that omits a result for being less notable: no value filters results out (see [Guidelines](#guidelines)).
- **Exit codes.** 0 success; 1 a command that explicitly gates (a regression check, a move verification or a gate the user configured) found a regression or a mismatch; 2 usage or config error, including an unknown config key; 3 environment error (not a git repo, shallow clone without a window, Node too old). Findings above a guideline never set 1. Errors are JSON on stderr when `--json` is set.
- **Schemas.** Each output has a JSON Schema in `schemas/`. A breaking change bumps `schemaVersion` and the plugin's major version.
- **Self-description.** `--help` on every command, `explain <rule>` for every recommendation rule, and `config explain`.
- **Reports.** `report <kind>` prints judgement slots and renders notes as HTML or Markdown (see [Reports](#reports)).
- **Maintainer commands.** A command or subcommand that calibrates or evaluates the suite on a corpus, such as `cochange risk backtest`, `cochange abandonment backtest` and `locality measure premise`, stays runnable and has its own `--help`, but is left out of its parent's `--help` listing, and no skill or reference that end users or Claude follow mentions it. Each plugin's spec describes its own in a "Maintainer commands" section. The outcome commands measure what a user acted on and stay user-facing.

## Shared vocabulary

- **Path**: repo-relative POSIX path.
- **Symbol id**: `path#Qualified.name`, with `~n` for duplicate names in one scope.
- **Tree distance**: `d(a, b) = depth(a) + depth(b) − 2·depth(LCA(a, b))` over folders, with files at their folder's depth. Every plugin uses this one function.
- **Component**: a named group of paths from the optional `components` globs in config.
- **Consumer**: a file or symbol that references a unit, classified as a direct call, another reference (value, registration, decorator) or a test reference.
- **Fan-in**: the number of distinct consumer files.
- **Code smell**: in Fowler's sense, a surface indication that usually corresponds to a deeper problem in the system. A smell is a prompt to investigate, not a defect.
- **Code health**: what the suite quantifies, as CodeScene uses the term: how easy code is to understand and change. CodeScene derives one 1 to 10 score per file from 25 or more factors whose weights it does not publish. The suite reports the underlying measures one by one, each with its evidence, and gives no single score (principle 1).
- **Guideline**: a numeric value that orders and annotates results (see [Guidelines](#guidelines)).

## Guidelines

Many of the measures have a value that practice or the literature treats as a point worth a look: four function arguments, a cyclomatic complexity of 9, 80 % confidence. The suite uses such a value as a **guideline**, a heuristic for investigation, and never as a cut-off that decides what is shown or whether a run passes.

- **Annotate, do not decide.** A result carries its raw measured value and where it sits against the guideline: the `guideline` value, the `ratio` of value to guideline, or a band word such as "above guideline". Results are ordered by how far past the guideline they are, so the most notable come first.
- **Cap, do not filter.** A result below a guideline is still listed. Output is capped by an explicit limit (`--limit`, top N) and reports how many results were left out. The limit is overridable and is the only cap. The one stated exception is locality's `minDistance`: a unit whose move would gain less than the guideline is not a recommendation candidate, and `summary.placed` counts those units so nothing goes without a count.
- **Evidence floors are the exception.** A statistic that means nothing below some sample size keeps a minimum: coupling from one shared commit, or a significance test on a handful of tasks. Below its floor an item is reported as `low confidence`, and listed where it can be, not dropped.
- **Wording.** Findings, skills and help text say "worth a look", "investigate" or "above guideline". They do not say "violation", "fails" or "too complex". The exception is a rule the user declares, such as a layer rule in `layers`: an import it does not allow is a `layer-violation`, because the user wrote the rule and `structure check` gates on it.
- **Configurable, with a source.** A guideline is a named key in config, described as a guideline in the schema. Where a plugin groups them, they sit in a `guidelines` object. Its default records where it comes from: a CodeScene document (their published default-rules template), a book (for example Tornhill's *Software Design X-Rays*), or a judgement call.
- **Gates are explicit.** Exit code 1 belongs to commands that gate on a regression or a user's own configured gate. A plain finding above a guideline never sets it.
- **Literal wording.** Specs, skills, help text and messages say what the tool does: "prints", "omits", "sorts by", "exits with 1". Established technical terms (code smell, code health, hotspot, change coupling) are kept in their defined sense.

## Evidence strength

Every output that uses history includes an `evidence` block, so neither the agent nor the user mistakes a sparse history for a strong signal:

- **Repository level**: months of usable history, logical changes in the window, active contributors, and a grade (`strong`, `moderate`, `weak`) read against configurable guidelines for each.
- **Per finding**: the support behind it (shared changes, revisions per side), and whether it is below the minimum for its grade. A finding below it is marked `low confidence` and still listed.

Usable history excludes:

- **Imported history**: a repository migrated from another VCS, or started with a bulk "initial import" commit, has a history that begins mid-life. A first commit adding a large share of the current tree is detected, and the window starts after it.
- **Shallow clones**, detected and reported as truncated.
- **Merge-policy changes** (moving to or from squash merges). They are not excluded, but each policy changes what a commit means, so a shift in the median commit size is reported, and the agent may choose a window within one policy.

Skills use the grade. With `weak` evidence they rely on static signals, present history-based findings as tentative, and do not let co-change overturn a static recommendation. With `strong` evidence, co-change wins where it disagrees with static structure, as each plugin spec says.

## Shared caches

- Location: `.cache/code-health/` at the repo root. On first use the CLI writes `.cache/code-health/.gitignore` containing `*`, so nothing needs adding to the repo's own `.gitignore`. Nothing is ever written inside the plugin folder, which is replaced on update. Everything in the cache can be regenerated, so clearing it costs time and nothing else.
- `history.sqlite`: commits keyed by SHA, each with its changed paths, numstat and renames. It is maintained by the `history` package and bundled into every plugin that reads history, so any of them can refresh it. Commits are immutable, so stored rows are never invalidated. A refresh adds the commits reachable from the analysed ref that are not yet stored, and every query selects by reachability from that ref. Switching branches or rewriting history costs only the commits that are new. A schema version number triggers a rebuild on mismatch, and a write lock makes concurrent refreshes safe.
- `blame.sqlite`: line authorship, the commit behind each line range of each file, per path and blob. It is kept apart from `history.sqlite`, has its own schema version and write lock, and is maintained by the `history` package for abandonment and change risk. A stored blame is reused while the file's blob is unchanged and no commit since it was made has touched the path, so a refresh blames only changed files. It holds no identities: the mailmap and identity decisions are applied when it is read, so changing either never needs a re-blame. See [abandonment.md](abandonment.md#concepts).
- `parse/`: parse results keyed by git blob SHA and grammar version. Unchanged files are never re-parsed, and historical revisions can be analysed by blob.
- `reports/<plugin>.<command>[.<variant>].json`: the results cache. A stored result is the complete result of a command, stamped with the commit and config hash it was computed from, and it holds every result: `--limit`, `--fields` and the path filter of a printed run change what is printed, never what is stored. A command that keeps results here prints the stored one when it matches and otherwise computes the result and stores it, so a report is written on demand and not only after a full run. One module in the `history` package (`results-cache`) does the reading, the keying and the writing for every plugin.
  - **Key.** A stored result matches when its stamped commit is the analysed commit (the commit the configured ref names, not the working tree), its config hash is the effective-config hash, its file name carries the same variant, it was written by the same code (`codeIdentity`: the SHA-256 of the content of the running bundle's `.mjs` files, computed once per process; from source, the size and modification time of the `packages/*/src` files), and the inputs it records for what else the result depends on are the current ones: the identity decisions and local mailmap stamps (`identityInputs`), and for a hotspot ranking the complexity report it was ranked with (`complexityReport`). The variant is the first 12 hex digits of the SHA-256 of the canonical JSON (keys sorted) of the command's own options that change the full result and that the run states, such as `--since` and `--until`, `--by`, `--all-files`, `--file`, `--min-degree`, `--min-support`, a layer, a metric list, a ranking order, or the path arguments. A run that states none has no variant, so its report keeps the plain name that other plugins read. Every other file in the folder is a variant of the same command.
  - **Stored by.** `cochange hotspots`, `cochange coupling`, `complexity files` and `complexity analyse` store every run, each variant under its own name, and print the stored result on a match. `complexity explain` stores its breakdown by the file's content, so a file that did not change is not parsed and an edited file is broken down again. `cochange brief` computes from three stored results, the default hotspot ranking, the default coupling pairs and `cochange.units` (per file: its revisions, its recent revisions and its last change in the window), for the window it states. When any of the three is missing or out of date it reads history once, stores all three and prints; when all three match it reads no history and does not refresh it, and a path that is not in the tree is answered from history because following renames needs it. A run with `--with-fixes` is never stored, because it reads the history of earlier revisions.
  - **What changes a result.** A new commit, a changed config and a changed identity file each give a result that no stored one matches. The history cache is then refreshed incrementally, the result is computed once and stored, and the runs after it read it. Uncommitted edits do not change a history-based result (hotspots, coupling, brief), so those are stored and read from a dirty tree, stamped as describing the commit. A result about the code as it stands (`complexity files`, `complexity analyse`) describes the commit only on a clean tree: with uncommitted work the run measures the files on disk, each file of which the parse cache has already by content unless it changed, and stores nothing.
  - **What a run says.** A run that printed a stored result lists it in `inputs.resultsCache`, an array of `{ report, head, config }`, one entry per stored result it read, and `meta.report` is `{ "stored": true }`. A run that computed the result has no `resultsCache`. `--no-cache` computes the result again and stores it in place of the old one. The files a stored run left out (`dropped`, `omittedByBuiltinExcludes`) are stored with it and printed again, so a printed stored result and a computed one carry the same counts. The columns and notices a table run prints are stored in the report's `meta.printed`, the only part of `meta` a report holds.
  - **A run that stores nothing** says so in `meta.report` with the reason: a run with `--no-refresh` that had to compute (its history may be behind the commit), a run with `--with-fixes`, a run over uncommitted work, an analysed commit that is not HEAD for a command that stores only reports about HEAD, or, for the commands that have not adopted the results cache (`cochange` risk commands, `structure` and `locality` analyses), the reasons they gave before: a path argument, a filter, a date window, a non-default view, a dirty tree. `structure evidence`, `structure packages` never store a report. A plugin may read another's report when its stamp matches the current HEAD. It names the report in `inputs`, and it must work without it. Reads run one way only (cochange reads complexity and locality, structure reads locality), so no result depends on the order the plugins were run in. A reader never computes another plugin's report, because the plugins share no code beyond the packages bundled into each.
  - **Concurrency.** A result is written to a temporary file beside its report and renamed into place, so a reader sees the whole old report or the whole new one. Commands running at once each compute and each rename, and the last rename stays; the results are equal, because both are a function of the same key. A report that cannot be parsed, or that lacks its stamps, is a miss.
- **Worktrees.** `history.sqlite` and `parse/` are content-addressed, so linked worktrees share the main worktree's copies. Reports are per worktree.

### Local state

State that cannot be regenerated never goes in the cache. It lives in `.code-health/local/` at the repo root, which the CLI creates with its own `.gitignore` containing `*`: activity overrides, a local-only mailmap and identity decisions, and measurement baselines. Files a team chooses to share, such as committed identity decisions, sit beside it in `.code-health/`.

## Languages

### Analysis layers

Every plugin's analysis is built in three layers. Each one works without the layers above it.

| Layer | Input | Works for | Provides |
|---|---|---|---|
| **History** | git log, numstat, blame | Every file, every language | Co-change, hotspots, spread, age, abandonment, identities, change stability, hidden coupling, change magnets |
| **Lexical** | Indentation, plus an optional per-family lexer profile: comment and string delimiters, block style (braces or indentation) and a branch-keyword list | Any text file and any historical blob, at best effort: indentation metrics always, profile metrics where a profile fits | Indentation complexity, bumpy road, nesting, approximate function blocks and their length, keyword complexity, append-shaped edits, lexical duplication |
| **Structural** | Tree-sitter grammar plus a language adapter | Tier 1 and tier 2 languages | Exact units and metric definitions, import and symbol resolution, dominator units, census, deterministic moves |

The lexical layer is the lowest common denominator. Its indentation metrics (indentation complexity, nesting, length) need no profile and apply to any text file. Lexer profiles are data, not code, and add comment and string stripping, keyword complexity, approximate function blocks and the per-function metrics built on them. A C-family profile covers C++, C#, Java, Kotlin, JavaScript, TypeScript, Go and Rust, and an indentation profile covers Python. A GLSL profile, with the C comment and `#` preprocessor rules, `struct` declarations, C-style function headers and `^^` among the short-circuit operators, covers the extensions `glsl vert frag geom tesc tese comp mesh rgen rint rahit rchit rmiss rcall`. It has no structural adapter to measure it against, so its per-function values are released without an agreement and marked unverified, as for a profile mapped by config. Conditional compilation is read as written, so a function header repeated by `#if` and `#else` is read as two nested blocks. Other languages can be mapped to a profile in config, through the top-level `languages` key (file extension without its dot, to profile name: `{ "zig": "rust" }`), but nothing outside tier 1 and 2 is tested or promised.

Lexical values are approximations, offered at best effort and labelled as such. A language gets whatever the layer can measure for it, and the output says what was skipped.

For tier 1 and 2 languages the structural layer checks the lexical one (see [Testing](#testing)). Per-function lexical metrics are reported for a language only when its measured agreement clears the configured bar, and the agreement rate travels with them. Below the bar, and for files with no profile, the layer reports file-level metrics only. A language mapped to a profile by config has no measurement behind it, so its per-function values are marked `unverified`.

Every output says which layer produced each value (`source: history | lexical | structural`). When the structural layer is available it wins, and the lexical value can be shown alongside for comparison. The lexical layer is also what makes history-wide analysis affordable: trends over hundreds of past revisions run on the lexical layer, without parsing any of them.

### Tiers

Tree-sitter WASM grammars run through `web-tree-sitter`, with no native builds. A plugin ships the grammars for every supported language and loads only those present in the repository.

| Tier | Languages | Support |
|---|---|---|
| **1** | TypeScript/JavaScript, C#, C++ | All three layers, with full adapters for every plugin |
| **2** | Python, Go, Java, Kotlin, Rust | All three layers, with full adapters for every plugin, added in roughly that order. Java and Kotlin share one JVM graph, so mixed projects resolve across both. |
| **0** | Everything else | History layer, plus best-effort lexical metrics: indentation metrics always, profile metrics only if the language is mapped to a profile. No deterministic moves and no import-graph units. |

Within tier 1 the build order was TypeScript, then C#, then C++, from easiest to hardest resolution. TypeScript also has a mature codemod (ts-morph) for deterministic moves. All eight adapters are supported: each passes the conformance fixtures of every plugin.

An adapter is **supported** only when it passes the shared conformance fixtures for every plugin that uses it. Only supported adapters analyse a repository and ship grammars. An **experimental** adapter is registered and tested but is not used to analyse a repository and ships no grammar: it runs only under test, through `overrideSupportedAdapters()`. The tables on this page are the explicit list of supported languages. A file in any other language gets the history layer and what the lexical layer can measure, and each output says which layer produced each value.

**External tools are optional.** Each language's confirming or moving tool (the Roslyn language server, clangd, jdtls, the Kotlin language server, gopls, rope, rust-analyzer) is used when installed. A missing tool never fails a command. The move output's `confirmations` array has one entry for each moved language that has such a tool, with `status` `confirmed` or `not confirmed` and the tool's name, and a missing tool gives `not confirmed` with a detail saying it is not installed. The array is always present and is empty when no moved language has a confirming tool (TypeScript's codemod, ts-morph, is itself the check). A reader tells a verified move from an unverified one by that status. Conformance suites that need a tool skip with a notice when it is absent. A language is one adapter behind one contract, registered by one line, with one file per language in each plugin that has language-specific tables, so adding a language does not edit a shared module (see CONTRIBUTING.md, "Adding a language").

### Dependency models

A language adapter turns source into file and symbol dependencies. Languages differ in how dependencies are written, so adapters work in one of two modes, and the graph package consumes both the same way.

- **Import-based**: a statement names a file or module (TypeScript, Python, Rust `mod`/`use`). The resolver maps specifiers to files.
- **Symbol-based**: a statement brings in a namespace, or nothing at all (C# `using`, Java, Kotlin and Go same-package references, C++ declarations visible through headers). The adapter builds a table of declared types and members per file, then resolves referenced identifiers against it to derive file edges. The resolution is heuristic: it follows names without overload or template resolution, so it is good enough for ranking. Before any move, references are confirmed with the language's LSP server.

### What the structural layer reads

These definitions are shared by every adapter. They decide fan-in, layer findings, coupling and locality findings, so they are stated here.

- **Unit.** A function, an arrow function, a method or a class. An overload signature and an abstract or interface member are not units, and the implementation is. A member of an object literal is a unit only when the literal is bound directly to a named variable. A function or lambda with no name of its own is not a unit: its branches count in the enclosing unit's metrics, as the nesting columns of the metric tables below say. CodeScene reports anonymous functions separately and does not document how a nested function's branches count, so this is the suite's own policy. A lambda bound to a name is a unit.
- **Call and reference.** A call counts only when the imported binding itself is called (`parse(x)`). `service.method()` is another reference to `service`, because without types the file that declares `method` is not known. The consumer classes are a direct call, another reference and a test reference.
- **Type-only imports** still count as references and as dependencies, because a type is a coupling. The edge records that it is type-only.
- **Specifier resolution** (TypeScript and JavaScript) tries tsconfig `paths`, then `baseUrl`, then workspace packages, and otherwise records an external. Other adapters resolve as the language notes say.
- **Test file.** Each adapter's `isTestPath` says. For TypeScript and JavaScript it is `*.test.*` and `*.spec.*`, and files under `test`, `tests`, `__tests__` and `__mocks__`.
- **Barrel and pass-through.** A barrel is a file with no units whose exports are all re-exports. An import that is only re-exported creates no edge, and consumers get an edge to the file that defines the name.
- **Private imports in Rust.** A module's own `use` declarations are visible to its child modules, so `use super::Name` resolves through a parent's private `use` to the item it imports. No other language follows an import as if it were an export, and the adapter turns this on with its resolver's `importsAreVisible` flag.

### Unit names in C++

A unit id is the enclosing namespaces joined with `::`, then `::`, then the class chain and the member joined with `.`. `A::B::m`, where `A` is a namespace and `B` a class, is `A::B.m`. A nested class is `A::B.C` and its method `A::B.C.m`. A free function in namespace `A` is `A::f`, and one in the global namespace is `f`. The id is the unit's identity across revisions, so classes of one name in different namespaces have different ids, and `trends`, `diff`, hotspots and function history match on it.

- **Nested namespace definitions.** `namespace A::B { }` is the same as `namespace A { namespace B { } }`.
- **Anonymous namespaces.** An anonymous namespace adds no segment, because its contents are visible only in their own file and the file path already separates them.
- **Inline namespaces.** An inline namespace adds its own name like any other namespace, because the name is part of the declared qualified name. `inline namespace v2 { int f(); }` gives `v2::f`.
- **Out-of-line definitions.** The namespaces around the definition come first. The adapter reads one file at a time, and resolves the written qualifier against the classes that file defines, trying the enclosing namespaces from the innermost outwards and taking the longest class chain. With `namespace A { class Outer { class Inner { void m(); }; }; }` in the file, `void A::Outer::Inner::m() {}` and `namespace A { void Outer::Inner::m() {} }` are both `A::Outer.Inner.m`, the name the member has when it is defined inside the class. A class defined later in the file is found too. Where no class of the file matches, because the class is declared in a header the file includes, the adapter does not follow includes, and uses this rule: the last segment of the qualifier is the class and every earlier segment a namespace, so `void a::B::m() {}` is `a::B.m`, `void c::free() {}` is `c.free`, and `void A::Outer::Inner::m() {}` is `A::Outer::Inner.m`. A nested class defined out of line in a source file whose class is in a header therefore has a different id from the same member defined in the header, and the two are not matched by `trends`, `diff` or function history.
- **Test-framework macros.** The grammar cannot read `TEST_CASE("name") { ... }` (doctest, Catch2) and the like: it sees a statement missing its semicolon and a stray block. At the top of a file or in a namespace the adapter reads the invocation as `void <name>()`, and a macro whose name contains `SUITE` or `NAMESPACE` as `namespace <name>`, where `<name>` is the invocation's text after its first five characters (its first ten for a namespace) with each character outside `A-Za-z0-9_` written as `_` and the last two characters standing for the parentheses: `TEST_CASE("a: b")` is the unit `CASE__a__b`, and `TEST_SUITE("terrain")` the namespace `__terrain__`. Inside a function body, such as a doctest `SUBCASE`, it is a plain block, so its decisions count in the function that holds it. Positions do not move. The name keeps only part of the macro's own name, which GoogleTest's `TEST(Suite, Name)` shows: that already parses, as a function named `TEST`, and repeats are `~2`, `~3`.
- **Overloads and repeats.** A second unit with the same id in one file gets `~2`, a third `~3`, in source order. The suffix covers a C# or Java overload, which has the same name and different parameters, and a repeated name in any language. It is part of the stable unit id, so a unit is matched across revisions by it, and a page prints it as `Name (variant 2)` (`Outer (variant 2).method` when the repeat is an enclosing unit).

### Metric definitions per language

The shared engine counts as complexity.md defines the metrics. These are the readings of each language's constructs, which each adapter's construct map implements and `complexity explain` repeats.

| Language | Decisions beyond `if`, loops and `catch` | Free | Nested functions and jumps |
|---|---|---|---|
| TypeScript/JavaScript | each `case`, the ternary, `&&`, `||`, `??` and their assignment forms | optional chaining | callbacks and arrow functions nest; a labelled `break` or `continue` costs a flat 1 |
| C# | each `case` label, each arm of a switch expression except the catch-all `_`, the ternary, `&&`, `||`, `??`, `??=`, and the pattern combinators `and` and `or` | `?.`, `!`, `is`, `await`, `yield`, `lock`, `using`, `finally`, relational patterns | lambdas, anonymous methods and local functions nest; `goto` costs a flat 1 |
| C++ | each `case` (not `default`), the ternary, `&&`, `||` and the tokens `and`, `or` | preprocessor branches, which are parsed as written | lambdas nest; `goto` costs a flat 1 |
| Python | `elif`, each `match` case except `case _`, `and`, `or`, the conditional expression; a comprehension's `for` and `if` clauses and a `match` guard add to cyclomatic only | `not`, comparison chains, a loop's `else`, `with` | `lambda` and nested `def` nest |
| Go | each `case` of `switch`, type `switch` and `select`, not `default` | `defer`, `go`, `if err != nil` is an ordinary `if` | function literals nest; a labelled `break` or `continue`, and every `goto`, cost a flat 1 |
| Rust | every `match` arm, the wildcard included, `&&` and `||` also in let chains and guards, `while let`, `if let` | `?`, `\|` between patterns | closures nest; a labelled `break` or `continue` costs a flat 1 |
| Java | each `case` label (not `default`), the ternary, `&&`, `||`; a `switch` expression and statement are one node | no null-coalescing operator exists | lambdas nest; a labelled `break` or `continue` costs a flat 1 |
| Kotlin | each `when` entry with a condition (not `else`), `&&`, `||` and the elvis operator `?:`, which is a cyclomatic decision as `??` is and free in cognitive complexity; `if` is an expression, so there is no ternary | safe calls `?.` and `!!` | lambdas, anonymous functions and local functions nest; `break@label` and `continue@label` cost a flat 1 |

## Reports

A report is a page for a person to read: the CLI computes the data and renders HTML or Markdown, and the agent writes only the judgement. The design is shared, so every report has the same two steps, the same page and the same rules. The code is `packages/report` (the protocol, the page shell and the components, bundled into each plugin) and `packages/cli-kit/src/report-command.ts` (the command wiring). Agents follow [shared/reports.md](../../shared/reports.md), which every skill carries as `references/reports.md`.

### Command and protocol

Each report is `<plugin> report <kind> [args]`, in two steps.

1. **`--slots`** prints JSON: the report kind, a `stamp`, the `data` the report will show, and the judgement `slots`. The stamp holds the protocol version, the kind, HEAD, the config hash and the report's `inputs`: its arguments, its window, and the stored results of other plugins that it read. A slot has an `id`, a `title`, what it is `about` (a file, pair, unit, finding or the whole report, with a ref and a label), the `task` (what to write), and its allowed shape: `verdicts` (an enum; empty for a text-only slot) and `maxChars`. A slot that asks the agent to choose subjects from the data has `choose: { max, candidates }`.
2. The agent writes `notes.json`: `{ "stamp": ..., "notes": { "<slot id>": entry } }`, with the stamp copied unchanged and one entry per slot id: `{ verdict?, text }`, or `{ items: [{ subject, verdict?, text }] }` for a choosing slot. **`--notes FILE --format html|md [--out PATH]`** renders it. Without `--out` the page goes to stdout.

Rendering refuses, with exit 2 and a message that names every problem, when the stamp does not match (another HEAD, config hash, kind or inputs), when a slot has no entry or an empty text, when an entry names a slot that does not exist, or when a verdict, a subject, a field or a length is not allowed. Every number on the page comes from the CLI's data and never from the notes: notes text is printed as written, escaped.

`--format md` without notes may render a data-only draft with the slots marked "not yet written", for terminals and quick looks. HTML requires notes. `--format md --compact` renders the short header used in a pull request comment. `--slots` takes none of `--notes`, `--format` and `--compact`. The common options `--limit` and `--fields` do not apply to a report: each report states how many rows each list leaves out.

A report reads other plugins' stored results only through the results cache, as [Shared caches](#shared-caches) says, names each one it read in the stamp's `inputs`, and never computes another plugin's result. A result that is missing becomes a line saying which command to run.

**Stored build.** `--slots` stores the report's build in `.cache/code-health/report-builds/`, and the rendering step reads it instead of computing the report again, so a render takes as long as reading a file. A stored build is reused only when all of these are unchanged: the kind, its arguments, its option values (except `--slots`, `--notes`, `--format`, `--out` and `--no-cache`), the directory the command ran from, HEAD, the config hash, the running code (`codeIdentity`, as for stored results), whatever the kind names in its optional `dependsOn` (the change report names the commits its range resolves to and the content of its `--evidence` files), and the size and modification time of the stored results in `.cache/code-health/reports/`, the identity files (`.mailmap`, `.code-health/identity-decisions.json` and the local ones), `.gitattributes` and the shallow file. A tree with an edit to a tracked file or an untracked file that is not ignored (the `--notes` and `--out` files excepted) neither reads nor stores a build. The history and blame stores are not compared: they are keyed by commit and blob. `--no-cache` computes the report again and stores the new build. One entry is kept per kind and arguments, so the folder does not grow with each commit.

The `--slots` output has the schema `report.schema.json` in the plugin's `schemas/`. A report's goldens (slots, HTML and Markdown) sit in `test/golden/_reports/`, and its tests cover the refusal cases.

### Page rules

- **HTML** is one self-contained file: inline CSS and inline SVG, no script needed to read it, no external request. It uses semantic elements (header, nav, main, section, table with caption, `th scope`, figure and figcaption). Class names say what a thing is and never how it looks. Every chart has a text table of the same data. Colour is never the only signal: values are printed, and a value beside its guideline has a marker and words. Text and fills meet WCAG AA contrast. A light and a dark theme follow `prefers-color-scheme`, and print styles drop the navigation and keep charts and tables whole.
- **Markdown** uses headings, lists and tables only, and reads on GitHub and in a terminal.
- **Header.** Every report shows the repository, the analysed commit, the date (HEAD's committer date, never the wall clock), the config hash, the evidence grade, the history window and what was excluded, with counts. A **Limits** section closes every report: fixed statements that follow from the data, then the agent's own limits slot when the report defines one.
- **Empty content.** A ranked table with no rows and a stability chart with fewer than 3 points print one line that begins "Notice:" in place of the block, naming what is empty (and why, when the block's `emptyText` says). A section whose blocks are all empty or notices prints as one line, `Heading: ...`, in place of its heading and blocks, and keeps its anchor in the navigation. A report builder calls `dropEmptySlots` on its finished build so that no judgement slot is asked for about content that is empty.
- **Capped tables.** A builder that cuts a ranked table to its first N rows uses `capRows`, and the table then prints "N of M shown; the rest are in `<command>` output." with the command that lists every row.
- **Compact header.** `--compact` prints the repository as a code span (escaped when the name has backticks) and the excluded counts as a total and the number of kinds, such as "Excluded: 420 in total across 5 kinds; the full report lists each". The full header lists each count.
- **Guidelines** are shown as legend values beside the numbers and never as a single score or a red, yellow and green rating. A list is a distribution or a top-N and says how many rows it leaves out. No headline figure is an average weighted by lines of code.
- **Names of people** appear only where the plugin already allows them (abandonment and successors with `--names`), and the knowledge report follows the same rule.

### Components

Components are pure functions from data to strings, one for HTML (with inline SVG where it is a chart) and one for Markdown, each with golden tests and an accessibility test. A section holds blocks, each a component's data tagged with `type`.

| Block `type` | What it renders |
|---|---|
| `ranked-table` | Rows in the order given, an optional rank column, and a guideline legend with a marker on the marked side of each column's guideline. With no rows it prints one notice line, from `emptyText` or "<caption>: no rows.". `capRows` cuts it and sets `fullIn`, the command that lists every row. |
| `treemap` | A squarified treemap nested by folder. The caller chooses the size and colour keys. Tiles print their name and value, colour is five numbered bands, and a table lists the tiles. Tiles not drawn are counted. |
| `category-treemap` | A squarified treemap nested by folder whose tiles are coloured by kind rather than by a value. Each tile prints its name and a short mark of its kind, hatched tiles have no kind, a legend lists the marks in words with their tile counts, and a table lists the tiles. Tiles not drawn are counted. |
| `sparkline` | A small line over periods, with a table of the values. |
| `histogram` | Counts per bin as bars with printed counts, and a table with shares. |
| `matrix` | A heatmap of rows by columns with the values printed in the cells, and a table. A caller may mark cells (an expected pair, a dependency against the layering, a missing partner): the mark's symbol prints after the value in the cell and the table, and the legend names each mark with its cell count. | `guideline-bars` | Values each against its guideline, with the ratio and "above guideline", "at guideline" or "below guideline". |

| `facts`, `paragraph` | A two column table of measures, and a paragraph. |

## Testing

The testing style is classic TDD with sociable tests. Mocks are reserved for process boundaries.

- **Fixture repositories.** Scripts in `fixtures/` build real git repositories in temp directories with fixed author and committer dates, so their histories are reproducible. Tests run the real CLI against them. There are no mocked git or parser layers.
- **Golden outputs.** JSON output per fixture is compared byte for byte. An intentional change updates the golden file in the same commit.
- **Algorithm properties.** Graph algorithms (dominators, LCA, coupling) are checked against naive reference implementations on generated graphs. For dominators, the reference is the textbook iterative data-flow method: *d* dominates *n* exactly when removing *d* disconnects *n* from the root. SCC condensation is checked by confirming that no unit splits a cycle.
- **Conformance fixtures.** Each language keeps small source fixtures with hand-verified expected values in `fixtures/languages/<id>/`, one folder per area: the adapter's units and dependency edges, each metric, interface shape, census mechanisms, packages and boundary findings, and file moves. Every plugin that uses the adapter runs the areas it owns, and a language is supported only when they all pass. Suites that need an external tool skip with a notice when it is not installed.
- **Lexical agreement.** Tier 1 and 2 languages have both layers, so the structural layer is ground truth for the lexical one. A corpus per language (the adapter and metric fixtures, plus files with the awkward shapes: lambdas, nested classes, expression-bodied functions, C++ macros and templates) runs through both, and lexical function blocks are matched to structural units by start and end line. The result is an agreement rate per profile and language: units found, units with exact boundaries, and spurious blocks. The rates are recorded in the repository, one file per language, and checked in CI, so a profile change cannot make them worse unnoticed. They decide where per-function lexical metrics are reported (see [Analysis layers](#analysis-layers)).
- **Skill evals.** `claude plugin eval` cases in each plugin's `evals/` cover triggering (the skill loads on relevant prompts and not on unrelated ones) and behaviour (it runs the CLI, respects grace periods and commit discipline, and cites red flags). The model and judge model are pinned explicitly (neither is by default), and a cost ceiling is set. Evals run on demand and before release, not on every push, because each run is billed.
- **Validation.** `claude plugin validate --strict` runs on the marketplace and every plugin in CI.
- **Self-check.** `npm run check:self` runs the suite's bundled commands on this repository, one after another because they share the cache, and is part of `npm run check` and CI. It is a gate this repository configures for itself and exits with 1 on any import cycle `structure cycles` reports, a command that exits non-zero, a source file the parser reports syntax errors in, or a source file the `exclude` globs hide. It compares nothing with a base: the repository holds no cycle, so a cycle that appears is the regression. CodeScene gates on a change in code health against the base, so that existing debt does not block unrelated changes. A repository that adopts the same gate with cycles it already has needs that comparison.

## Release

- Each plugin is versioned with semver independently. A breaking JSON schema change is a major bump, and a change in recommendation output for the same input is at least a minor bump, called out in the changelog.
- CI gates: build reproducibility, the version-bump check (from the first public release), the full test suite, plugin validation and schema checks of the golden outputs.
- Team adoption: commit `extraKnownMarketplaces` and `enabledPlugins` in the project's `.claude/settings.json`, then each collaborator runs `claude plugin install <plugin>@code-health --scope project` once per clone.

## Measurement across the suite

Each plugin defines its own outcome measure, and the suite shares the instruments:

- **Change spread** (from the history cache): mean pairwise tree distance of files per logical change. Each file is placed at its path as of that change, so a later move never rewrites the spread of earlier changes.
- **Agent effort** (from Claude Code session transcripts in `~/.claude/projects/`): files read, distinct folders visited, re-reads and tokens per task, from tool calls and from the files named in `Bash` commands. The transcript format is internal to Claude Code and can change, so one module reads it. Only paths and counts are extracted. Measurement is local by default, and any team aggregation exports counts and repo-relative paths only, never content. The rules that fix every number:
  - **Sessions.** Only a transcript whose version matches `2.1.x` is measured. A session of another version, or with no versioned message, is listed as not measured with its version and reason, and counts toward neither side of a comparison. Two kinds of transcript are read. A top-level session file (`~/.claude/projects/<encoded root>/*.jsonl`) gives main tasks, and its sidechain lines are skipped. A subagent file (`<session>/subagents/**/agent-*.jsonl`, with an `agent-*.meta.json` beside it) gives one task, measured from its sidechain lines, so no line is counted twice. Each task records `source` (`main` or `subagent`), and a subagent task also records `agentType` and `description` from the meta file when it exists, the description being a short label written by the orchestrator. Subagent files are counted as measured or not measured apart from main sessions. A command can read `main`, `subagent` or `all` tasks. A task is also given `shellCalls` and `unparsedShellCalls`, the number of `Bash` calls in it and the number whose command was not parsed (see Shell commands below), and `effortMode`, the setting below.
  - **Effort mode.** `--effort tools|all` (default `all`) chooses what the totals count. `tools` counts only the `Read`, `Grep`, `Glob`, `Edit`, `Write`, `MultiEdit` and `NotebookEdit` tools, which is the only thing effort counted before shell commands were read. `all` counts those and the files named in the commands of `Bash` calls. A task keeps its tool and shell counts apart whatever the mode: `tool` and `shell` each hold `reads`, `filesRead`, `reReads`, `searches` and `edits` as if the other did not exist, and the totals (`reads`, `filesRead`, `reReads`, `searches`, `edits`, `foldersVisited`, `readPaths`, `editedPaths`) are over the origins the mode names. A file read through a tool and through the shell counts once in `filesRead`, and the second read is a re-read, so the two parts can sum to more than the total. The mode also decides which tasks exist, since a task with no counted edit to a repository file is left out: a task that edited only through the shell is a task with `all` and absent with `tools`.
  - **Shell commands.** The transcripts module reads the `command` of each `Bash` call for the files it names, and nothing else leaves it: paths and counts. It splits the command into words, operators, redirections and here-docs, resolves each relative path against the `cwd` recorded on the line and against any literal `cd` earlier in the same command (a `cd` inside a subshell ends with it), and maps the path as it maps a tool path, including the worktree rule. A path outside the repo, under `.git` or in `node_modules`, or starting with `~`, is not counted. These commands are read:
    - Reads: `cat`, `tac`, `head`, `tail`, `less`, `more`, `wc`, `nl`, `od`, `xxd` and `bat` on their file operands, `sed` without `-i` and `awk` on their file operands (the script is the first operand unless `-e` or `-f` is given), `perl` without `-i` on its file operands, `grep` on its file operands, `grep -r` and `rg` on an operand whose last segment has an extension, `diff` on both operands, `git show <rev>:<path>` (the path is relative to the top of the repo), `< file`, and `python`, `python3`, `node`, `ruby`, `tsx`, `ts-node`, `deno`, `bun`, `sh` and `bash` on the script named as the first operand when its last segment has an extension.
    - Edits: `sed -i`, `perl -i` (and `-pi`), `> file`, `>> file`, `&> file` and `2> file`, `tee`, `cp` (the destination), `mv` (source and destination), `rm`, `git mv` and `git rm`, and here-doc writes such as `cat > file <<EOF`. `rm -r`, `cp -r` and an operand ending in `/` name directories and count nothing. A target of `/dev/...` counts nothing. `cp` and `mv` to a directory count the file under that directory.
    - Searches: a glob operand of any reading command, `grep -r`, `rg` and `diff -r` on an operand that is a directory or has no extension (or on the working directory when it names none and is not fed by a pipe or `<`), and `find` on its starting paths. A glob counts as a search, never a read, and an edit command given a glob is not parsed.
    - Compound commands: `&&`, `||`, `;`, `|`, `&`, newlines, `( )` subshells, `{ }` groups, leading `VAR=value` assignments, a literal `VAR=value` assignment earlier in the command (substituted into `$VAR` later), and `for NAME in <literal words>; do ...; done`, including nested loops, whose body runs once per word. `time`, `command`, `env` and `sudo` are skipped. A command that is not in the table (`ls`, `git status`, `npm test`) is understood and counts nothing. Every command in a line counts as run: the commands after `||` and in both branches of an `if` are not told apart, which is why `if` is not parsed.
    - Not parsed: command substitution (`$(...)`, backticks, `<(...)`), brace expansion, `if`, `while`, `until`, `case`, `select` and function definitions, a `for` over a glob, a variable or a command's output, `eval`, `xargs`, `source`, `exec`, `nohup`, `timeout`, `sh -c` and `bash -c`, `find` with `-exec` or `-delete`, inline code given to an interpreter (`python3 -c`, `node -e`, a here-doc or `-` for stdin), a `cd` to a variable or to `-` followed by a relative path, a file operand of a reading or editing command that holds a variable, and an edit of a glob. A call that is not parsed is counted in `unparsedShellCalls` and contributes no path at all, including the paths of its commands that parsed on their own. Nothing is guessed.
  - **Worktree paths.** Claude Code worktrees at `<root>/.claude/worktrees/<name>/` are deleted once their work is merged, so `git worktree list` no longer names them. A path under `<root>/.claude/worktrees/<name>/` maps to the same relative path in the repo, for the main root and any other root. A subagent's meta `worktreePath` and the worktree its recorded `cwd` lies in map the same way, and a transcript whose `cwd` is in one of them belongs to the repo.
  - **Prompt.** A user line that is not a tool result and is not meta, sidechain, a compaction summary, transcript-only text or an `[Request interrupted by user` marker, and whose origin is absent or human.
  - **Task.** In a main session, one prompt and the agent turns that follow it, up to the next prompt. In a subagent file, the first prompt and every turn after it in the file. A task with no counted edit to a file of the repository is left out, counting the edits the effort mode names. A task records `shellCalls` and `unparsedShellCalls` over all its `Bash` calls, including those that named no repository path, whatever the mode.
  - **Read, search, edit.** A read is a call of the `Read` tool on a repository file, or (with effort mode `all`) a file named as a read operand in a `Bash` command. `Grep` and `Glob` count as searches, as does a glob or a directory searched in a `Bash` command. An edit is `Edit`, `Write`, `MultiEdit` or `NotebookEdit`, or (with `all`) a file named as an edit target in a `Bash` command. A re-read is a read of a file the same task already read, through either origin.
  - **Parsed share.** An effort summary carries `shell`: `calls`, `unparsed` and `parsedShare`, parsed calls divided by calls to 3 decimal places (null when there were no `Bash` calls), over the tasks the summary covers. Commands that print results print it as a summary line on stderr when the tasks made any `Bash` call, such as `Shell: 126 Bash calls in these tasks, 16 not parsed, parsed share 87.3%.`. A parsed call is one every command of which was understood. It does not say the call named any file.
  - **Tokens.** The task's total is input, output, cache read and cache creation tokens, summed over its turns, taking the last usage line written for each message.
  - **Window.** `from` is inclusive and `to` is exclusive, both UTC, applied to the prompt's timestamp. Means and medians are rounded to 2 decimal places.
  - **What is not seen.** With effort mode `tools`, no `Bash` call is seen. With `all`, the files named in the parsed commands above are seen, and these are not: files edited by a script that computes its paths (a loop over `$(...)` or a glob, `xargs`, `find -exec`, `python3 -c`, a build or a code generator), reads made inside test runs, builds and compilers (`npm test`, `tsc`, `vitest`), reads and edits by any command not in the table (`jq`, `sort`, `touch`, `patch`, `git checkout`, `git apply`), files reached through a symlink or a variable, directories where the extension rule takes a file for a directory (a file such as `Makefile`), and everything in an unparsed call. The reads, edits and tokens a main-session task spent through a subagent are not in that task either, since they are a subagent task of their own, so a main task that delegates looks cheaper than it was and the two halves of one piece of work are measured apart. Every figure is a lower bound. The same bias applies before and after, which a comparison relies on, and a report states it where it states sample sizes.
- **Before and after windows**: baseline before the first change, then compare over a matching window afterwards, with the same filters. Reports state sample sizes, and the skill does not claim an effect the data cannot show.
- **Comparison group**: findings are acted on because they are extreme, and extreme values drift back towards the average when left alone. Each comparison therefore sets the acted-on files beside candidates of similar rank that were not acted on, and reports the difference between the two groups, not the raw before and after.
- **The suite's own commits**: refactoring commits made through the skills carry a `Code-Health:` trailer naming the plugin and rule. They are left out of outcome windows, since a move commit is wide by construction.
- **Independence**: a measure that a tool moves by construction is a leading indicator for that tool, whatever it is elsewhere. Change spread falls whenever files that change together are co-located, so for locality the independent outcome is agent effort (see [locality](locality.md#measurement)).

## Build order

Each plugin spec has its own milestones. Across the suite, the order is set by what the measurements need:

1. The history core and `cochange spread`, because every outcome in the suite is measured with them and a baseline cannot be taken afterwards.
2. A premise check, before any mover exists: from existing history and session transcripts, test whether tasks that touch more distant files cost more reads and tokens. Locality's priority depends on the answer. It is `locality measure premise`, a maintainer command, which reports the sample, the evidence and what the data does not show.
3. The lexical layer with its agreement test, then the TypeScript adapter.
4. Analysers and baselines for locality and complexity, then the commands that change code.
5. Structure, which builds on locality's graph and cochange's coupling, then its packaging skill.
6. Identities, then abandonment and change risk, which share the blame cache.
7. Further languages, in tier order.

## Roadmap

Candidate plugins, each to get its own spec before work starts:

- **idioms**: replacing thin wrappers and re-implementations with standard-library or platform idioms (out of scope for locality).
- **duplication**: clone detection, reporting only, built on the lexical layer (normalised token windows) so it works in every language. The remedy is judgement, and creating shared helpers needs consumer evidence first.

## Decisions

- **Plugins, CLIs and skills; no MCP servers.** The work is batch-shaped, a CLI is testable and usable in CI, and nothing costs context until a skill calls it.
- **Self-contained bundles over runtime plugin dependencies.** Each plugin installs and works alone. Composition is optional and goes through report files.
- **Committed `dist/`.** Installation copies git content, so the build must be in git. CI keeps it honest.
- **One config file for the suite.** Repositories configure exclusions and entry points once.

## Open questions

- Whether to also publish the CLIs to npm for CI use outside Claude Code, or have CI call the bundles from a checkout of this repo.
- Where team-level aggregation of transcript metrics should live, if anywhere.
- Whether to stop committing `dist/` to the main branch. A marketplace entry's `source` can name a `ref`, so CI could build a release branch instead. That would end the conflicts that committed bundles and mandatory version bumps cause between any two open changes, and would keep the WASM grammars, shipped once per parsing plugin, out of the main history.
